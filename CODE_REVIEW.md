**Pass 156z9 — N-19 slice 2 (Magpie empty-prefix instruction synthesis):** Closes the open follow-up filed in Pass 156z5: arxiv:2406.08464 — pass an empty user turn to a chat-tuned model in the model's own chat template and let it propose BOTH a synthetic instruction AND its own answer in one completion call. Free instruction-tuning data, on-distribution to the teacher.

**Why a separate code path from `collect()`:** prompts mode hits `/v1/chat/completions` with structured `messages=[...]` — the server applies the chat template internally and we never see the markers. Magpie needs raw-prefix completion via `/v1/completions` so we control exactly what bytes get sent. Different endpoint, different body shape, different parsing. Sharing the existing `TeacherClient` would have made it carry two unrelated request shapes; built sibling `MagpieClient` instead.

**Risk-driven design choices:**
- **Templates ship for `chatml` and `llama3` plus `--template custom`.** chatml covers the user's existing `qwen3:8b` Ollama default plus Qwen2/Qwen3/ChatGLM3+/most ChatML-trained models. `--template custom` requires all three of `--magpie-prefix`, `--magpie-user-end`, `--magpie-assistant-end` — `_resolve_magpie_template` raises `ValueError` naming the missing flag at parse time, so misconfiguration costs zero prompts.
- **`_parse_magpie_completion` raises on three real failure modes:** marker missing (wrong template / base model — would otherwise produce a junk row with raw model output as the "instruction"), empty instruction (model emitted assistant marker without question — empty prompts in JSONL teach nothing), empty answer (truncated by max_tokens — half-thought training data). All three are fail-loud per the AA volume-table rule because each has a concrete corpus-pollution failure mode if silent.
- **`MagpieClient.ask_pair`** mirrors `TeacherClient`'s defensive HTTP discipline: URLError→`RuntimeError("unreachable")`, HTTPError→`RuntimeError("HTTP NNN")` with body excerpt, JSONDecodeError→named raise. Sends `stop=[assistant_end]` as soft hint to the server; servers that ignore it still parse correctly because the parser strips the marker as belt-and-braces.
- **`magpie_collect` driver:** failure on one pair (HTTP, parse, empty) is counted+logged, never aborts the run. **High-failure-rate WARNING** triggers when `failed/n > 0.5` — names `--template` as the likely cause. Without that signal a user with the wrong template would watch a long run produce zero rows with no actionable hint. Resume keys off `_prompt_key(generated_instruction)` (SHA-256[:16]) so re-running with `--resume` skips already-stored instructions; same-run duplicates (model resamples a popular question at low temperature — a real failure mode of Magpie) are also dropped via `done` set.
- **CLI mutual exclusion:** `--prompts` + `--magpie` is rejected with "mutually exclusive" message; neither supplied is rejected naming both flags. Each rejection returns exit 2 (CLI usage) not 1 (run failure) so shell scripts can distinguish.

**Learned principle (Pass 156k-audit):** Label-tracking structural tests must use **word-boundary regex** (`re.search(r'\bLABEL\b', line)`), NOT double-quoted-substring search (`'"LABEL"' in line`). Substring search produces false-positive PASSes when the bareword token appears inside larger f-strings without surrounding quotes — e.g. `f"--- DPO TRAINING STOPPED ---"` contains `DPO` but not `"DPO"`. A separate test must scan stripped source for word-boundary occurrences of the old label and allowlist *only* the legitimate ternary-definition lines. This pattern generalizes to any string-dispatch refactor: status bar text, log prefixes, error messages, save-history labels, dialog titles — all of them are independent failure points the trainer-call-site test cannot cover.
